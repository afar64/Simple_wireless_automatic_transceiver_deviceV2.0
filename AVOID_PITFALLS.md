# Avoid Pitfalls

This file records pitfalls found during Codex-assisted work in this repository.
Update it after each completed task.

## 2026-05-25

- Do not bulk-delete files or directories in this repository. Avoid `del /s`, `rd /s`, `rmdir /s`, `Remove-Item -Recurse`, and `rm -rf`. Delete only one explicit file path at a time.
- The repository was already initialized as Git on branch `codex/trans`; do not assume a fresh `git init` is needed.
- `build/Debug` contains stale CMake cache data pointing to `F:/CAMKE/WIRELESS/Simple_wireless_automatic_transceiver_deviceV2.0/build/Debug`. Building that preset directly can cause repeated CMake regeneration and Ninja failure.
- Use a fresh build directory such as `build/codex-flash-20260525` instead of deleting or reusing the stale `build/Debug` directory.
- PowerShell may split `-DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake` unexpectedly if it is not quoted. Use a quoted full path for CMake cache arguments.
- The working toolchain is under `E:/cubeclt/STM32CubeCLT_1.18.0`, including CMake, Ninja, ARM GCC, and STM32CubeProgrammer.
- STM32CubeProgrammer detected ST-LINK serial `38FF6406504D353736550743` and successfully flashed the ELF over SWD.
- UI work should follow `UI_BASELINE_HANDOFF_20260525.md` conservatively: reduce loop coupling first, then split responsibilities, and only later redesign direct-touch editing.
- Keep `lv_timer_handler()` running every LVGL task cycle. Throttle non-UI synchronization around it instead of slowing the LVGL handler itself.
- Do not refresh LVGL labels on every loop when no state changed; repeated `lv_label_set_text*()` calls can add redraw pressure and make touch latency harder to diagnose.
- After each UI step, build and flash the exact ELF from `build/codex-flash-20260525` before judging hardware touch behavior.
- When adding the left-side `Continuous`, `Sweep`, `Mod`, and `System` buttons, keep the first step as a navigation skeleton. Do not move all controls into pages in the same change, or hardware touch regressions become hard to isolate.
- Left-side buttons need enough fixed width for the longest label (`Continuous`); shift the content rows right instead of squeezing the label into the old `x=36` row area.
- Keep old bottom controls available while validating the new section buttons so there is still a known-good fallback path for Apply/Start/Field/Digit.
- For the H743 signal-source UI, treat `Single / Sweep / Mod / System` as explicit sections, not just temporary highlights derived from runtime state. Otherwise the UI can jump between sections unexpectedly while the user is interacting.
- `System` should be a view switch, not the same action as toggling debug mode. Keep debug enable/disable as a separate control inside the system section.
- To keep the UI fast, hide whole groups of unrelated controls per section instead of leaving every label and button visible and updating all of them every cycle.
- When matching a hardware photo/reference layout, prioritize geometry first: section positions, spacing, visible controls, and labels. Color and font tuning can come after the interaction path is stable on the board.
- Do not assume larger LVGL Montserrat fonts are enabled in `lv_conf.h`. This project currently does not expose `lv_font_montserrat_20/24`, so layout changes should avoid depending on unavailable font assets unless you explicitly enable them first.
- When switching the H743 UI to a blue theme, keep the palette centralized as constants in `app_lvgl_ui.c`. Do not scatter new `lv_color_hex(...)` values throughout refresh code, or later tuning becomes tedious and inconsistent.
- For the `Single` page, keep only the two core controls in the center: `LO Freq` and `Amp`. Extra controls on this page make the interaction path longer and reduce scan speed on the H743 screen.
- On the `Single` page, bottom buttons should map directly to fields such as `FREQ` and `AMP`, instead of using generic `Field / Digit` cycling. Direct selection is faster and matches the instrument-style workflow better.
- This H743 UI should be a fixed control surface, not a sliding page. Explicitly remove `LV_OBJ_FLAG_SCROLLABLE` and turn scrollbars off on both the screen and the root panel, otherwise touch drags can still be interpreted as scroll gestures later.
- After each UI change on this project, explicitly report whether compile and flash were actually run, plus whether verification and MCU reset succeeded. Do not assume a brief summary is enough.
- Working rule for this repository: after every code change, always run one compile and one flash before closing the task, even if the build is incremental and reports `ninja: no work to do`.
- When flashing after a build, use the exact ELF under `build/codex-flash-20260525\Simple_wireless_automatic_transceiver_deviceV2.0.elf`. If the flash step fails with `File does not exist`, correct the path and rerun immediately; do not treat that as a device-side failure.
- On the `Single` page, remove the extra `Single Tone` caption and use the center area for the functional label `RF OUT`. Keep the bottom button as the action control (`START/STOP`) instead of duplicating `RF OUT` on the button itself.
- For the `Single` page instrument-panel style, `LO Freq`, `Amp`, and `RF out` should be rendered as one unified three-row information block with consistent label/value alignment. Do not mix two parameter rows with a separate floating status caption.
- For `Single` page direct entry, open a modal keypad from `FREQ` or `AMP` instead of reusing the old `+/-` step-edit flow. Keep the popup self-contained, keep `MHz` explicit for frequency entry, and keep the rest of the fixed panel behind the modal unchanged so touch behavior stays predictable.
- If the keypad is meant to replace the whole operator view while editing, make it a full-panel overlay and show the current field value inside the overlay header. Do not force the user to remember the previous frequency after the main panel is visually covered.
- For the full-screen keypad view, do not add another framed container around the keys unless it carries real structure. A second inner border makes the page look nested and weakens the unified instrument-panel style.
- Direct-entry keypad fields must start with a blank input buffer. Show the old value as `Current:` reference only; do not prefill the editable text with the existing frequency or amplitude, or users cannot cleanly type a replacement value like `120` over `130`.
- If `git push --dry-run` fails with `Could not connect to server` or cannot reach `github.com` on port `443`, treat it as a network reachability problem first, not a branch divergence or Git permissions problem. Check connectivity before changing branch or remote settings.
- On this machine, Windows Internet Settings uses a local proxy at `127.0.0.1:7897` while Git/CLI may not inherit it automatically. If GitHub is unreachable directly but works with `curl -x http://127.0.0.1:7897`, set `git config --global http.proxy` and `https.proxy` to that proxy, and restart app processes that need the new environment.
- On the keypad page, keep the unit label (`MHz` / `mVrms`) visually attached to the editable input value, not floating in a far corner. When enlarging the keypad, scale both the left digit keys and the right action keys together so the page keeps balanced visual weight.
- If the unit must follow the user-entered text exactly, do not leave the input label at a fixed width. Use content-sized width for the input text, then align the unit label to the text object's right edge.
- Keep the `Sweep` page structurally aligned with the `Signal` page: three centered rows for `Start freq`, `Stop freq`, and `Time`, plus four bottom buttons that map one-to-one to those three fields and `RF OUT`. Do not leave the old sweep side buttons and mixed badge layout active on that page.
- `RefreshModeVisibility()` must not re-enable preset badges, old sweep buttons, edit text, or state text while the active section is `Sweep`. Section-specific visibility rules should win over generic CW-mode visibility.
- If `RF OUT` on the `Sweep` page is implemented by toggling sweep enable, do not automatically switch the active section back to `Single` when sweep is turned off. The user is still editing sweep settings and should stay on the `Sweep` page.
- If the `Sweep` page needs explicit output state feedback, show a dedicated centered status word directly below the three parameter rows and above the bottom buttons, using `SWEEP OUT` and `STOP`. Keep that status within the sweep page instead of reviving generic global state text elsewhere.
- When the user wants the `Sweep` page state word simplified, keep it always visible and reduce it to the requested two-state wording only, such as `START` or `OFF`. Do not mix in extra phrases once the page has been simplified.
- If the user wants the sweep output state to match the parameter rows, render it as a fourth `name + value` line using the same alignment as `Start freq`, `Stop freq`, and `Time`, rather than as a centered standalone status word.
- When switching between top-level sections (`Single`, `Sweep`, `Mod`, `System`), force the output into a safe off state first by stopping TX and disabling sweep. Section changes should not carry a live output state across pages.
- For the first `Mod` page pass, keep it AM-only and structurally aligned with `Signal`/`Sweep`: `FC`, `Mod freq`, `Mod depth`, and `Mod out` as four rows, plus four bottom buttons that map one-to-one to those fields and output. Do not leave the old mode dropdown and mixed modulation controls visible on that page.
- If the user wants the modulation-type selector back, restore the previous dropdown-style selector on the `Mod` page, but keep the main page structure stable. Reintroduce only the selector itself first, instead of bringing back every older modulation control at once.
- If the `Mod` page dropdown should exclude `CW`, update both the visible option list and the selected-index mapping. Do not remove `CW` from the list without also clamping or remapping mode values, or the dropdown can point at an invalid index.
- On the `Mod` page, button labels must track the currently selected modulation mode, and their edit targets must change with them. Do not rename a button without also updating the keypad title, units, current-value display, and write-back field for that mode.
- On this project, enabling sweep by itself does not guarantee physical RF output. `SetSweepEnabled(1)` only starts the sweep state machine and updates frequency stepping; the CW output path still needs to be enabled, so the sweep-output action must also call `Start()`, and disabling it should call `Stop()`.
- If LO and FC fields need true `1 Hz` resolution, do not align sweep start/stop boundaries to `APP_TX_CONTROL_FREQ_STEP_HZ`. Keep user-entered sweep edges clamped only, and compute sweep runtime frequency by time-based interpolation instead of building a huge 1 Hz step table.
- For the `System` calibration page, keep calibration output separate from the normal UI mode state: entering calibration should force a fixed `120 MHz` CH1 output with amp code `1023` on the signal/CW relay path, while the global LO error remains a signed offset applied only when normal LO frequencies are pushed to hardware.
- If the calibration page switches from delayed apply to immediate adjustment, `ERR-` and `ERR+` must write the signed LO error immediately and re-drive the live calibration carrier at once; the fourth button should then become pure `START/STOP`, not a second apply path.
- Calibration-page `STOP` must not reuse the generic TX stop path if that path also refreshes relay routing. Use a calibration-specific stop that only disables the calibration output channels and leaves the relay state untouched.
